3m28s to see what is due today. The target is 30 seconds.

Diagnosis, design system and incremental redesign of practice management software for law firms. Everything ties back to one problem: lawyers cannot miss a deadline, and today the interface doesn't let them see one.

Take-home exercise for a hiring process, done in 4 days on a trial account. Not commissioned by the company and not implemented in the product.

§ Problem

Three screens, three overdue counts.

33% of votes on the feedback portal ask for the same thing: don't miss deadlines. I tested that task on a trial account. It took me 3m28s to find out what was due that day, and the interface itself showed 1, 5 and 13 overdue items depending on the screen. For anyone working with court deadlines, an inconsistent count is worse than none.

§ My role

Take-home exercise, from diagnosis to component

Individual case for a legal tech company's hiring process for a Senior UX Designer. I did the diagnosis, principles, design system architecture and governance, migration plan and components, with no access to users, the team or the code.

§ Diagnosis

Creating a task works. Creating a deadline doesn't.

I combined three sources: portal votes, a task script tested on the trial, and a heuristic review of 20 audited screens. The table shows the core finding: the flow that matters most to lawyers is the one that fails most. A deadline saved as a task gets no alert.

§ Principles

Five decision rules, each tied to a problem

Problem 1

1. Show the day on one screen

Deadlines, hearings, tasks and events in one list, by urgency.

Problem 3

2. Keep overdue items visible

Overdue stays on screen until resolved, with color, icon and text.

Problems 2 and 4

3. Use the firm's vocabulary

Names and defaults that make sense to lawyers.

Problem 5

4. Standardize the activity

The same row in every module.

All

5. Change gradually, with one exception

Without breaking what users know. The exception is the overdue color.

§ Design system · architecture

Start with tokens, because they enter the legacy code without touching templates

The product runs on AngularJS. CSS variables are the only change that reaches the whole product at once without rewriting screens. So the system was designed in four layers, bottom-up.

1Foundations. Color, typography (Nunito Sans, already in the product), 4 px spacing scale, shape and icons.
2Three-tier tokens. Primitive holds the value, semantic holds the intent, component binds intent to the part.
3Components. Button, Input, Badge and Toast, then ActivityItem, WidgetCard and Modal.
4Patterns. Create activity, filtered lists and dashboard.
§ First visible effect

Three shades of danger red become one token: feedback-danger.

§ Governance

A component only joins the system if two squads use it

Any designer can propose; triage is weekly. If two or more squads use it, it becomes a system component. If not, it stays local for a quarter. The design specialist, front-end engineer and tech lead decide together, with tie-breaks by area: engineering on feasibility, design on visuals.

Figma and code share the same status (draft, beta, stable, deprecated). A component is only "done" with Figma, code and documentation.

§ Migration plan

Four phases, from lowest to highest risk

Priority: frequency of use × consistency or usability problem ÷ effort. New and old screens coexist during migration: swap component by component, and structural changes ship whole, behind a feature flag.

Phase 0

Tokens

Across the product. Sets up the overdue color.

Phase 1

Basic components

Button, fields, Modal, Toast and Badge. Solves problem 4.

Phase 2

Core flows

Create activity and the workspace, with ActivityItem and WidgetCard. Solves problems 1, 2, 3 and 5.

Phase 3

Everything else

The long tail and retiring the legacy.

§ Hard decision

Deadlines stop being red.

Today the Deadline type uses the same red as overdue dates. On one screen, a deadline three weeks out and an overdue task look identical. I considered three options:

AKeep deadlines red and mark overdue only with icon and text. Respects habit, but the color keeps two meanings.
BDeadlines in wine, red only for overdue. Chosen. Each color has one meaning, and the type is still written on the Badge.
CFour colors by urgency, as suggested on the portal. Clashes with the type colors and clutters the list.
§ The exception

The only change that goes against "change gradually"

A color with two meanings during migration is worse than an abrupt switch: on one screen red would mean deadline, on another overdue, and lawyers would be back to not knowing what has expired. So the switch ships in Phase 0, through the activity-prazo token, across Calendar, Kanban and modals in the same release. The cost is breaking the habit of seeing deadlines in red. The mitigation is a first-click test before release: "which items are overdue?".

§ Use of AI

AI sped up the audit and exploration. The decisions were mine.

I logged six uses of AI during the case. In five, I adjusted the output: I redid a schedule that invented tasks outside the brief, focused the test script on deadline tasks and changed the palette red so deadline and overdue wouldn't be confused. The component inventory of the 20 screens was the only output used as is. Choosing the focus, interpreting the test and deciding on the red didn't go through the tool.

§ Limitations

Individual evaluation on a trial account; votes only from portal users; no access to the team's current governance. The governance model is a starting point, to be adjusted to the existing process and the team's four designers.
